REVISION NOTES 2 (2026-10-08) - restructuring, validation, tests
=================================================
STRUCTURE: every service was restructured into the four layers required by the course specification. The file
paths in the original plan below map to the new packages like this (base package com.ecommerce.<service>):
  controller/*                -> presentation.controller   (controllers + one @RestControllerAdvice ApiExceptionHandler)
  dto/* (REST request/response)-> service.dto               (the service layer's API contract, also used as JSON)
  service/*                   -> service                    (application services: orchestration only)
  entity/*                    -> domain.model               (aggregates, entities, value objects - the business rules)
  exception/*                 -> domain.exception
  repository/*                -> domain.repository (PORT interface) + infrastructure.persistence (Spring Data + adapter)
  event/dto, event/consumer, event/producer -> infrastructure.messaging (+ .dto)  [Kafka/Spring Cloud Stream]
  client/*, config/*          -> infrastructure.client, infrastructure.config
  streams/*                   -> infrastructure.streams
Dependencies point inwards: presentation -> service -> domain <- infrastructure (infrastructure implements the ports
declared in the domain). The domain layer has no Spring/Kafka/HTTP code except JPA annotations on the aggregates.

WHERE THE ORDER SERVICE NOW DIFFERS FROM THE PLAN BELOW (Member 1)
- DOMAIN MODEL (Task 1.1 FILES 1-2): Order is an aggregate root with OrderItem inside it, status is the enum
  OrderStatus (stored as the same strings), money is the value object Money (2 decimals, never negative, embedded in
  the same columns total_amount / unit_price). Order has @Version for optimistic locking. All rules are methods on
  the aggregate: Order.place(...), confirm(), reject(reason), cancel(), isCancellable(). It records domain events
  (OrderPlaced, OrderConfirmed, OrderCancelled, OrderRejected) that OrderService publishes AFTER the transaction
  commits.
- PRICING + VALIDATION (Task 1.1): POST /orders no longer uses a fixed price. OrderService calls Inventory
  GET /products/{id} for every item (unit price = the product price) and Customer GET /customers/{id}. New error
  responses: 400 for unknown customer, unknown product, empty items, quantity <= 0, missing customerId; 503 if
  Inventory/Customer/Shipping cannot be reached (RestTemplate now has 2s connect / 5s read timeouts).
  New config: customer-service.base-url (http://localhost:8084). The ports are ProductCatalog, CustomerDirectory,
  ShipmentGateway; adapters are InventoryServiceClient, CustomerServiceClient, ShippingServiceClient.
- STATE RULES (Tasks 1.3/1.4): confirmOrder()/rejectOrder() only act on a PENDING order - a late
  InventoryReservedEvent for an order that was cancelled in the meantime is ignored (it used to flip CANCELLED back
  to CONFIRMED). A REJECTED order can no longer be cancelled (409).
- PUBLISHING (Task 1.2 FILE 7): OrderEventProducer was replaced by KafkaOrderEventPublisher, which translates domain
  events into the unchanged JSON envelopes (OrderCreatedEvent, OrderConfirmedEvent, OrderCancelledEvent). Event
  payload classes live in infrastructure.messaging.dto.
- CANCELLATION (Task 1.4): the eligibility rule is the domain service CancellationPolicy (order status, then the
  shipment status from Shipping, which is only fetched when the order status allows cancelling). OrderService.cancelOrder()
  is still the single entry point used by both the REST endpoint and the agent's OrderCancelTool.
- AI (Tasks 1.5/1.6): ProductLookupTool now uses the ProductCatalog port (and reports availableQuantity, not raw
  stock); OrderCancelTool also handles malformed ids and an unreachable Shipping Service.
- TESTS (new): domain tests (OrderTest, MoneyAndPolicyTest), application-service tests with in-memory fakes
  (OrderServiceTest) and a Spring Cloud Stream test-binder test (OrderMessagingTest) that proves the Kafka messages
  produced/consumed without a broker. Run with: mvn -pl order-service test

Method: cancelOrder(UUID orderId) -> OrderResponse

       updatedAt = Instant.now()
    7. Save

         orderId, items, previousStatus))
    9. Map to OrderResponse and return it
