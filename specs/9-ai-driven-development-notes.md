## 9.2 Representative decisions: accepted, rejected, modified

| # | AI proposal / starting point | What the team decided | Why |
|---|---|---|---|
| 1 | The task files said "Spring Cloud Stream / spring-kafka" and their code used `@KafkaListener` / `KafkaTemplate` | **Rejected** the spring-kafka code; migrated every service to Spring Cloud Stream (functional style, `StreamBridge`) | Reading the course specification showed Spring Cloud Stream is a **mandatory** dependency and extra dependencies need the coordinator's permission. The AI plan had treated it as optional - a reminder to check AI output against the actual requirements |
| 2 | Kafka Streams as a raw `StreamsBuilder` bean (plan, Task 2.3) | **Modified** to the Spring Cloud Stream Kafka Streams binder | Same requirement. Cost: two binders in one service needed isolated environments, per-function `applicationId`/`state.dir`, and took several debugging iterations (details in `1-architecture.md` §1.6) |
| 3 | Hard-coded `unitPrice = 74.99` marked "TEMP" in the plan | **Replaced** by a real price lookup in Inventory plus customer/product validation | Revenue and totals were meaningless; the spec asks for a realistic domain |
| 4 | Task spec contradicted itself on whether a rejection publishes `OrderRejectedEvent` | **Accepted** the acceptance-criteria reading (no event); removed the dead payload class, kept an internal domain event | Testable contract beats an ambiguous paragraph |
| 5 | Revenue counts every `OrderCreatedEvent`, including rejected orders | **Accepted** as is (decision: "the logic that requires less change") | Keeps the topology simple; recorded as a known limitation |
| 6 | Entities as plain setter classes with logic in services | **Modified** into DDD aggregates, value objects, domain events and domain services; four-layer package structure | Course specification requires a presentation/service/domain/infrastructure layering and a discussion of DDD patterns |
| 7 | A Spring `contextLoads` test for Shipping that needed a real broker (65 s, timeouts, and it stole messages from the running service) | **Replaced** by tests on the Spring Cloud Stream in-memory test binder | Tests must be fast, repeatable and not interfere with running services |
| 8 | Mockito-based service tests | **Rejected** in favour of hand-written in-memory fakes | The machine runs JDK 25 (the course needs 21, not installed), and Mockito's Byte Buddy is known to fail on that JDK (seen in another project in this workspace; not tried here). Fakes avoid the dependency on the JDK version and are also clearer for ports |

## 9.3 Defects found only by running the system (not by reading the code)
These make good "lessons learned" examples because each looked correct on paper:
- Two Kafka Streams functions in one service silently shared one `application.id`, so **both** returned empty results.
- Binding-level Kafka settings placed outside an isolated binder's `environment:` block were silently ignored
  (the producer then failed with a serializer `ClassCastException`).
- A stale background process from an earlier run kept a Kafka partition in the consumer group, making a *correct*
  configuration look broken.
- Spring Data does not discover repository interfaces nested inside another class.
- A late "stock reserved" reply could flip an already **cancelled** order back to **confirmed** (found by reasoning
  about the domain; now guarded and unit-tested).

## 9.4 Lessons learned (draft observations to refine)
- **Strengths:** speed on boilerplate (DTOs, adapters, repetitive tests); consistent code style across four services;
  good at producing structured documents and test matrices; useful for mechanical refactors (a small script moved ~60
  classes between packages and rewrote their imports).
- **Limitations:** plausible-looking output that violated a requirement nobody had re-read (decision 1); optimistic
  claims ("works") until the system is actually run; configuration-heavy frameworks (Spring Cloud Stream with two
  binders) needed trial and error that only real runs resolved; it cannot supply things it has no access to - the LLM
  agents' real replies need the team's own API key.
- **Process that worked:** keep the specification files and the code in step (every code change also updates the
  README/task notes); verify with an end-to-end script, not just compilation; write down deviations from the plan as
  they happen.
- **Impact:** large productivity gain on implementation and documentation; the human work shifted to checking against
  the requirements, deciding trade-offs, and running and judging the system.
