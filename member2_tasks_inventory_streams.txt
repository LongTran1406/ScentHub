ADDED AFTER THE ORIGINAL PLAN - TASK 2.5: TRENDING PRODUCTS (second real-time analysis story)

STRUCTURE: every service was restructured into the four layers required by the course specification. The file
paths in the original plan below map to the new packages like this (base package com.ecommerce.<service>):
  controller/*                -> presentation.controller   (controllers + one @RestControllerAdvice ApiExceptionHandler)
  dto/* (REST request/response)-> service.dto               (the service layer's API contract, also used as JSON)
  service/*                   -> service                    (application services: orchestration only)
  entity/*                    -> domain.model               (aggregates, entities, value objects - the business rules)
  exception/*                 -> domain.exception
  repository/*                -> domain.repository (PORT interface) + infrastructure.persistence (Spring Data + adapter)
  event/dto, event/consumer, event/producer -> infrastructure.messaging (+ .dto)  [Kafka/Spring Cloud Stream]
  client/*, config/*          -> infrastructure.client, infrastructure.config
  streams/*                   -> infrastructure.streams
Dependencies point inwards: presentation -> service -> domain <- infrastructure (infrastructure implements the ports
declared in the domain). The domain layer has no Spring/Kafka/HTTP code except JPA annotations on the aggregates.

WHERE THE INVENTORY SERVICE NOW DIFFERS FROM THE PLAN BELOW (Member 2)
- DOMAIN MODEL (Task 2.1 FILE 1): Product is an aggregate root with the value object Money for its price and
  @Version for optimistic locking. availableQuantity is derived (stock - reserved), never stored. Invariants live on
  the aggregate: name required, price/stock never negative, stock can never be lowered below the reserved quantity.
  Behaviour: Product.create(), update(), canReserve(), reserve(), release() (release clamps at 0 and reports it).
- VALIDATION (Task 2.1): invalid product data now returns 400 (blank name, negative/missing price, negative stock,
  stock below reserved) instead of a database error.
- RESERVATION (Task 2.2): the all-or-nothing rule is the domain service StockReservationService (works across several
  Product aggregates). Improvements over the plan: lines for the same product are SUMMED before checking, so an order

- USE-CASE CLASSES: ProductService (catalogue CRUD/search), StockService (reserveForOrder / releaseForOrder - what the
  Kafka consumer calls), AnalyticsService (low stock, revenue, trending). The old ProductService.reserveStock/
  releaseStock/findLowStock methods moved there. Concurrent updates: an OptimisticLockingFailureException is rethrown
  by the consumer so the binder retries the message.
- STREAMS: RevenueQueryService and TrendingProductsQueryService were replaced by the port OrderStatistics

--------------------------------------------------
MODIFY: ProductService.java — add 2 methods
--------------------------------------------------
Constructor-inject (add): InventoryEventProducer

Method: reserveStock(String orderId, List<OrderItemEventDto> items) -> void
  Logic:
    1. For each item, load the Product by productId (UUID.fromString(item.productId))
    2. Check: for EVERY item, is (stockQuantity - reservedQuantity) >= item.quantity?
    3. IF all items have sufficient available stock:
       - for each item: product.reservedQuantity += item.quantity; save
       - build InventoryReservedPayload(orderId, items)
       - inventoryEventProducer.publish("InventoryReservedEvent", payload)
    4. IF any item is insufficient:
       - do NOT reserve ANY items (all-or-nothing — a partial reservation
         would leave inconsistent state)
       - build list of InventoryUnavailableItemDto for the insufficient ones
         (include requested vs available amounts)
       - build InventoryRejectedPayload(orderId, "INSUFFICIENT_STOCK", unavailableItems)
       - inventoryEventProducer.publish("InventoryRejectedEvent", payload)

Method: releaseStock(List<OrderItemEventDto> items) -> void
  Logic:
    1. For each item, load Product by productId
    2. product.reservedQuantity -= item.quantity (never let it go below 0 —
       clamp to 0 if a negative would occur, and log a warning if that happens
       since it indicates a data inconsistency)
    3. Save each updated product
    (no event is published after release — this is a terminal step)

GOAL:
Expose two REST endpoints: low-stock (plain SQL query against current DB
state) and revenue (reads from the Kafka Streams state store built in Task 2.3).

DEPENDS ON: Task 2.2 and Task 2.3 complete.

FILES TO MODIFY:

--------------------------------------------------
FILE 1: LowStockResponse.java
--------------------------------------------------
Package: com.ecommerce.inventory.dto
Fields:
- UUID productId
- String name
- Integer availableQuantity
- Integer threshold

Example JSON output (as part of a list):
{
  "productId": "b2c3d4e5-0000-0000-0000-000000000002",
  "name": "Wireless Headphones",
  "availableQuantity": 3,
  "threshold": 10
}

--------------------------------------------------
FILE 2: RevenueResponse.java
--------------------------------------------------
Package: com.ecommerce.inventory.dto
Fields:
- Double totalRevenue

Example JSON output:
{ "totalRevenue": 4599.85 }

--------------------------------------------------
MODIFY: ProductRepository.java — add method
--------------------------------------------------
Add a custom query (using @Query with JPQL, since "available" isn't a
stored column):

@Query("SELECT p FROM Product p WHERE (p.stockQuantity - p.reservedQuantity) < :threshold")
List<Product> findLowStock(@Param("threshold") int threshold);

--------------------------------------------------
MODIFY: ProductService.java — add method
--------------------------------------------------
Method: findLowStock(int threshold) -> List<LowStockResponse>
  Logic:
    1. productRepository.findLowStock(threshold)
    2. Map each to LowStockResponse (availableQuantity = stockQuantity -
       reservedQuantity, threshold = the passed-in value)
    3. Return list

--------------------------------------------------
FILE 3: AnalyticsController.java
--------------------------------------------------
Package: com.ecommerce.inventory.controller
Annotations: @RestController @RequestMapping("/analytics")
Constructor-inject: ProductService, RevenueQueryService

Endpoint 1: @GetMapping("/low-stock")
  getLowStock(@RequestParam(defaultValue = "10") int threshold)
    -> ResponseEntity<List<LowStockResponse>>
  - return ResponseEntity.ok(productService.findLowStock(threshold))

Endpoint 2: @GetMapping("/revenue")
  getRevenue() -> ResponseEntity<RevenueResponse>
  - Double total = revenueQueryService.getTotalRevenue()
  - return ResponseEntity.ok(new RevenueResponse(total))

--------------------------------------------------
ACCEPTANCE CRITERIA
--------------------------------------------------
[ ] GET /analytics/low-stock?threshold=10 returns only products where
    (stockQuantity - reservedQuantity) < 10
[ ] GET /analytics/low-stock with no threshold param defaults to 10
[ ] GET /analytics/revenue returns the current running total matching
    what was verified in Task 2.3's testing
[ ] Both endpoints return valid JSON even when there is no data yet
    (empty list for low-stock, 0.0 for revenue — no errors)

--------------------------------------------------
IMPLEMENTATION STEPS
--------------------------------------------------
1. Add the low-stock query method to ProductRepository.java
2. Add findLowStock() to ProductService.java
3. Create the 2 response DTOs
4. Create AnalyticsController.java with both endpoints
5. Test both endpoints via Postman: seed products with varying stock
   levels, place a few orders, confirm both figures are correct
